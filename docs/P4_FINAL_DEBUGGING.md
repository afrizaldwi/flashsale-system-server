Root causes and evidence

- The original runner attached ledger, handshake and active-VU parsing only to `k6Proc.stdout`. `stderr` was accumulated without parsing, and handshake/VU parsing split individual chunks rather than complete buffered lines. The real K6 1.7.1 smoke run confirmed `stdoutHasHandshake=false`, `stderrHasHandshake=true`. K6 console logs use stderr on this installation. Escaped logfmt output also needs decoding before ledger JSON parsing.
- The running Nginx command was `nginx -c /etc/nginx/p3/active.conf -g daemon off;`. Running plain `nginx -T` inspected the unused default configuration; `nginx -T -c /etc/nginx/p3/active.conf` showed the actual bootstrap configuration with `location / { return 503; }`, and no upstream. P4 starts the P3 bootstrap script but does not run the P3 controller that normally installs routing.
- Before correction, ingress `/health` and `/products` returned Nginx HTML 503 responses. Direct backend `/health` and `/products` returned 200, with primary and standby available. Backend logs showed no corresponding application failure. Thus these ingress responses were generated by Nginx, before reaching checkout or the database.
- Docker DNS resolves the Compose service alias `backend`; the short names `backend-1` and `backend-2` did not resolve. Docker inspect identified both real backend endpoints as `172.21.0.5:3000` and `172.21.0.6:3000`. The fix discovers these endpoints rather than assuming hostnames.
- Product 1 had stock 9,999,907 before smoke traffic. Sold-out stock did not cause the incident. Deterministic selection of the lowest in-stock product ID is now part of baseline verification.
